## 2. Dispatch More v270 (commit `3da0a6a0`), what is in it

Why: Stream Check's round crawled (1334 of 6024 in 5 days, "73 days left"); the user rightly did not
believe the providers limited it ("when watching yourself it works no issue and you can change very
fast"). Found in the server's own log:

1. **One unanswered question left a provider out for the whole round.** `_login_problem` now returns
   `_NoAnswer` for a ConnectionError / timeout / page instead of an answer; `logins_of` rests the
   provider `LOGIN_RETRY_SECONDS` (300) and asks again next batch instead of `_unavailable`.
2. **Refusal counts carried over between rounds** (TiviBridge given up 6 s into a round).
   `_forget_blocks()` at `start_round` clears `BLOCK_FIELDS` from every provider's state.
3. **False limits.** Digitalizard (one connection) "learned" 8/57 min from two refusals the moment a
   viewer started, and 20/196 min from a block that lifted in a minute. Now: both refused + a viewer on
   the provider or YIELD -> "in use", no limit; both refused + `_ProviderCount.busy_now()` (provider
   asked fresh) says a login is in use -> "in use", no limit; answered again within `SHORT_BLOCK`
   (180 s) -> not a limit; otherwise the first sighting is only a `candidate`, and a limit is kept when
   a second sighting is alike (`CANDIDATE_ALIKE` 2x, within `CANDIDATE_DAYS` 7). `LIMITS_VERSION` 3 -> 4
   drops every limit learned the old way (Digitalizard's go by themselves on install).
4. **The page tells the truth**: a provider left for the round shows status "unavailable", the reason
   "...; tried again next round" and "since <time>" (`_unavailable` stores `at`).
5. **Compare pictures while checking** (the user: "open all 3 when possible record them and compare
   those 10 seconds ... suggest error and have the images ready to show"). Setting `compare_pictures`
   (default off), `compare_every_days` (7). `run()` -> `pictures_first()` before the providers' turns:
   - one long look first (`LONGER_KEY` zset `stream-check:pictures-longer`, oldest first, manual asks
     score 0): `picture_compare.compare_channel(..., may_open, opened, should_stop)` for 90 s; only
     this can say DIFFERENT;
   - then quick looks for the batch's channels not compared within `compare_every_days`: the
     channel's first stream on a free login plus one stream on every other free login, opened at
     once, each read by `probe(..., picture_seconds=10, fingerprint_seconds=10)`; the bytes are
     fingerprinted (`picture_compare.fingerprint`, 4 fps, a picture every 2 s), counted as checked;
     refused ones are left to their provider's turn;
   - `quick_compare`: SAME only with >= 10 matching moments, 80 %, clear by 40 points, offsets +-7 s
     and >= 5 s overlap; anything else PENDING -> queued for the long look. Measured on made-up
     programmes: 10/10 different ones pending, the same one 0-6 s apart always same.
   - verdicts on each stream record (`picture`: verdict, why, offset, against, at, long; carried by
     `_record`), pictures in `picture-compare:<channel>` (shown by the existing PictureCompare modal).
   - Page: "Different picture" badge per stream (click -> the pictures), "N different pictures" on the
     channel, view "Different picture (N)", counted in "Needs you"; button reads "See the pictures"
     once compared; Compare pictures pressed during a round queues it first (`with_check`).
   - `record()` reads a silent stream again without the sound output (ffmpeg refused an empty one; the
     old 90 s comparison had the same bug).
   Docs: `fork/picture-check.md` (v270 section at the top), HANDOVER §8 first bullet.

Not done / open on the server: the long look runs at most once per batch; no nightly-only schedule
(it runs with the round); the thresholds are from made-up programmes and should be checked against
the user's real streams once v270 runs.

  2. **The real bug (TiviBridge):** polling the provider's `active_cons` every 2 s next to the
     check's status showed, every batch: at the batch start a TiviBridge connection open ~66 s with
     `now=''` and no stream counted (= the **long picture compare**, `pictures_first` ->

     long-compare path never calls `provider_counts[key].check_ended()` (the quick looks and normal
     checks do), so `_ProviderCount.free()` has no `last_check_ended`, does not wait out
     PROVIDER_LINGER (45 s), and takes the provider's still-counted closed connection for a viewer.
     Every batch -> TiviBridge never gets checked while channels wait in LONGER_KEY.
- **Fix (uncommitted in `dispatcharr tsi`, working tree):** `apps/channels/stream_check.py`, in
  `pictures_first`, long path: wraps `opened` as `opened_long` that records the provider keys it
  opened, and in a `finally` after `compare_channel` calls
  `provider_counts.setdefault(key, _ProviderCount()).check_ended()` for each.
  Test added: `RunTests.test_the_long_compare_s_own_connection_is_waited_out_not_taken_for_a_viewer`
  in `apps/channels/tests/test_stream_check.py` -- **fails without the fix (`'ORF1A' not found in
